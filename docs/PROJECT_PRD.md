## 1. 一句话项目介绍

大学生脑内常任委员议会是一款把日常纠结转化为二次元多智能体议会审议的决策辅助应用，让用户在充满戏剧感的辩论、质询和投票后获得一份可执行的红头决议。

## 2. 问题与目标用户

### 2.1 用户问题

大学生经常在学习、睡眠、社交、恋爱、消费和未来规划等低风险但高内耗的选择上反复犹豫。常见的搜索或问答产品通常只能给出一段平直建议，难以还原用户脑内多个价值观相互拉扯的过程，也容易出现“分析结束了，但我还是不知道下一步做什么”的情况。

本产品要解决的不是专业领域的最终决策，而是：

- 把模糊的情绪和纠结拆解为几个可以被讨论的立场；
- 让用户看到不同利益相关者的理由、冲突和妥协条件；
- 将辩论结果收束为明确的行动、时间窗口和复盘条件；
- 在网络或模型不可用时仍能完成演示和基本决策闭环。

### 2.2 目标用户

- 以大学生为主，尤其是容易在深夜对日常选择反复思考的人群；
- 喜欢二次元、游戏化、互动叙事或“逆转裁判式”表达方式的用户；
- 想获得结构化建议，但不喜欢传统严肃咨询界面的用户；
- 黑客松评委、产品体验者和希望快速展示多智能体交互效果的开发者。

### 2.3 非目标用户与边界

本产品不替代医生、律师、心理咨询师或持牌金融顾问，不适用于急救、诊断、法律责任、投资交易等高风险场景。产品输出应被理解为自我反思和行动整理的辅助材料，用户保留最终决定权。

## 3. 产品目标与成功标准

### 3.1 产品目标

1. 在 1 分钟内让用户完成一次有反馈、有冲突、有结论的议会体验。
2. 让用户能理解“为什么得到这个结论”，而不是只看到一条无来源的建议。
3. 让最终决议至少包含一个下一步行动、一个行动时间窗口和一个复盘条件。
4. 在线模型不可用时，自动降级到程序化引擎，保障演示和核心流程可完成。
5. 在不保存用户 API Key 的前提下，提供 Gemini、OpenAI 兼容接口和离线模式。

### 3.2 成功指标

| 指标 | 目标 |
| --- | --- |
| 首屏进入议会成功率 | ≥ 98%（以有效请求计） |
| 从提交问题到出现首个状态 | ≤ 1 秒（SSE 已连接时） |
| 议会流程完成率 | ≥ 70% |
| 生成决议后的行动确认率 | ≥ 40% |
| 在线模型失败后的兜底完成率 | ≥ 95% |
| 关键接口 4xx/5xx 比例 | ≤ 5% |

## 4. 解决方案与核心创新

### 4.1 解决方案

用户输入一个纠结的问题，或直接选择睡眠、绩点、社交、恋爱、钱包、未来等预设议题。系统召集 11 位拥有不同价值函数的脑内委员，依次完成立案、发言、用户质询、投票、裁决和行动确认，最后输出一份带有红头、公章、执行细则和复盘节点的正式决议。

### 4.2 核心创新

1. **多价值函数人格化**：将 GPA、睡眠、快乐、钱包、社交体面、尊严、未来、恋爱、野心、道德和身体状态映射为不同委员，使抽象的内耗变成可观察的观点冲突。
2. **可观看的实时审议**：通过 SSE 逐段传输台词、当前发言者和阶段状态，用户不是等待一个黑盒答案，而是在“观看”答案形成。
3. **用户保留最终裁量权**：投票结果提供集体建议，但用户可以选择 A/B/C 任一方案作为最终执行方案，避免产品替用户做出不可逆决定。
4. **生态校准而非固定模板**：用户可录入年级、专业、睡眠负债和焦虑源；专业类型会调整委员权重，生成更贴近个人处境的讨论重点。
5. **二审机制推动证据化反思**：用户可以提出一次不可抗力或新证据，系统重新组织计划、票型、决议和发言，避免只改标题、不改结论的“伪上诉”。
6. **在线智能与离线可靠性并存**：在线模型用于生成更灵活的讨论，运行时校验保障结构稳定；调用失败时使用程序化引擎，保持完整可演示流程。

## 5. 用户旅程与状态流转

```text
空闲首页
  ↓ 输入问题 / 选择预设 / 恢复本机历史
立案中（SSE 连接）
  ↓
情况分析
  ↓
议会辩论 → 用户当庭质询
  ↓
投票与合议
  ↓
选择最终执行方案 A / B / C
  ↓
红头决议
  ├─ 接受方案：记录确认状态并展示执行动作
  ├─ 提起二审：输入新证据，最多触发一次修正
  ├─ 分享：生成裁决海报
  └─ 恢复：从本机最近 3 条记录继续查看
```

### 5.1 关键体验原则

- **先反馈，后等待**：建立 SSE 后立即显示“立案中”，避免用户误以为页面失效。
- **先呈现冲突，后给结论**：委员之间必须存在可理解的立场差异。
- **结论必须可执行**：决议不能只给态度，要有下一步、时间窗口和触发条件。
- **戏剧化服务于可理解性**：爆闪、音效和公章强化记忆点，但不阻塞阅读和操作。
- **用户始终能退出或回退**：支持关闭质询、跳过校准、恢复本机记录和选择最终方案。

## 7. 功能需求

### 7.1 P0：核心闭环

| 编号 | 功能 | 验收标准 |
| --- | --- | --- |
| P0-01 | 输入议题 | 用户可提交自定义问题，输入经过长度限制和危险内容清洗 |
| P0-02 | 预设议题 | 至少支持睡眠、学习、社交、恋爱、消费和未来方向等预设 |
| P0-03 | 议会生成 | 返回可渲染的委员、发言、计划、票型和决议结构 |

| P0-06 | 方案选择 | A/B/C 方案可选，选择结果必须进入最终决议和接受状态 |
| P0-07 | 裁决展示 | 红头文件显示动态案号、日期、行动摘要、执行窗口、置信度和免责声明 |
| P0-08 | 二审上诉 | 新证据会同步影响计划、票型、结论和发言；同一裁决最多上诉一次 |

| 编号 | 功能 | 验收标准 |
| --- | --- | --- |
| P1-01 | 心智生态校准 | 可编辑年级、专业类型、睡眠负债和焦虑源；专业会影响委员权重 |

## 8. 技术架构与接口

### 8.1 技术分层

```text
Next.js App Router / React UI
  ├─ 首页与议会交互组件
  ├─ SSE 消费与 JSON 兼容回退
  ├─ 本机历史、模型设置和分享海报
  └─ 无障碍、打印和 reduced-motion 适配
          ↓
Next.js Route Handlers
  ├─ 输入清洗、限流、错误脱敏
  ├─ Gemini / OpenAI-compatible provider dispatch
  ├─ 运行时脚本归一化与字段校验
  └─ 程序化引擎兜底
          ↓
Council Domain Model
  ├─ MeetingScript
  ├─ AgentSpeech
  ├─ Plan / Vote
  └─ Resolution
```

### 8.2 API 清单

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/council` | 查询服务信息、版本和支持的 provider |
| GET | `/api/council/health` | 查询服务健康状态、能力和安全配置摘要 |
| POST | `/api/council` | 通用议会生成入口 |
| POST | `/api/council/debate` | 生成完整议会剧本 |
| POST | `/api/council/stream` | 以 SSE 逐段返回议会过程 |
| POST | `/api/council/interrogate` | 处理用户对委员的当庭质询 |
| POST | `/api/council/appeal` | 基于新证据生成一次二审修正案 |

### 8.3 Provider 策略

- `gemini`：调用 Gemini API，默认使用服务端环境变量或本次请求提供的配置；
- `openai`：调用 OpenAI Chat Completions 兼容接口，支持自定义 `baseUrl` 和模型；
- `procedural`：不依赖网络和密钥，使用程序化议会引擎；
- 所有在线返回都必须经过运行时归一化，缺失字段、非法枚举或异常结构自动回退。

## 9. 数据结构与隐私边界

### 9.1 主要数据结构

- `ApiConfig`：provider、apiKey、baseUrl、model；其中 apiKey 仅存在当前内存状态。
- `UserEcologyProfile`：年级、专业类型、睡眠负债、焦虑源、委员权重。
- `CouncilMeetingScript`：案号、日期、情况分析、委员发言、计划、票型、决议和上诉状态。
- `CouncilResolution`：结论、获胜方案、下一步行动、行动窗口、置信度、假设和免责声明。

### 9.2 隐私边界

- 浏览器端 API Key 不进入 localStorage；
- 本机历史只保存在当前浏览器 localStorage，不发送到独立历史服务；
- 服务端日志和错误消息不应回显完整 API Key；
- 生产环境应配置正式密钥管理、日志脱敏和数据保留策略。

## 10. 安全、可靠性与可访问性要求

### 10.1 安全要求

- 对用户议题、追问和生态画像执行长度限制、HTML 清洗、危险协议过滤和提示词边界隔离；
- 默认不信任代理转发的 IP Header，只有明确配置 `TRUST_PROXY_HEADERS=true` 且部署在可信代理后才读取；
- 当前限流器是进程级滑动窗口，多实例部署必须在网关或 Redis 层追加共享限流；
- OpenAI 兼容自定义地址仅允许 HTTPS，并拒绝 localhost / 私有 IPv4 / IPv6 目标；
- CORS 不开放为通配符，生产环境应按域名和部署架构配置；
- 所有模型输出必须经过 schema-like 运行时校验，避免非法结构直接进入 UI。

### 10.2 可靠性要求

- SSE 建连后立刻返回初始状态；
- SSE 中断时客户端可回退到 JSON 请求；
- JSON 请求失败时使用本地程序化引擎；
- 上诉操作采用完整 amended script 替换，确保计划、票型、发言和决议一致；
- 构建、Lint、TypeScript 检查和 API 回归测试必须作为发布前检查。

### 10.3 可访问性要求

- 弹窗使用 `role="dialog"`、`aria-modal` 和可识别标题；
- 所有关闭、复制、分享和播放控制提供可读标签；
- 支持键盘 Escape 关闭临时窗口；
- 支持 `prefers-reduced-motion`，降低震动、闪烁和过渡效果；
- 打印时隐藏操作工具栏，只保留可归档的裁决正文。

## 11. 视觉与交互规范

- **视觉关键词**：机关红头、赛博法庭、二次元角色、玻璃拟态、黑白红高对比；
- **情绪节奏**：首页留白制造悬念，立案显示速度感，辩论制造冲突，裁决提供秩序和收束；
- **操作反馈**：按钮点击、发言切换、异议爆闪和投票结果必须有明确状态变化；
- **信息层级**：当前发言和下一步动作优先于装饰信息；
- **失败体验**：模型失败时显示“已切换离线引擎”，不展示内部错误、密钥或供应商堆栈。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 用户把娱乐性结论当专业建议 | 高 | 显示免责声明，限制产品定位，后续增加高风险话题拦截 |
| 模型输出格式不稳定 | 中 | 运行时归一化、字段校验和程序化回退 |
| 多实例限流失效 | 中 | 明确进程级限制，生产接入网关或 Redis |
| 过多动效造成疲劳或不适 | 中 | reduced-motion、打印模式和清晰关闭入口 |
| 在线服务延迟或不可用 | 高 | SSE 早反馈、JSON 回退、离线引擎 |
| 自定义 API 地址被滥用 | 高 | HTTPS、私网地址拦截、输入校验和部署侧网络策略 |
| 用户历史误以为云端备份 | 中 | 明确标注“仅保存在本机”，后续提供导出/删除能力 |
